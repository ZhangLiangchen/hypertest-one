# Cloud 测试任务使用流程

本指南描述 [ADR-038](architecture/ADR-038_TASK_FOCUSED_CLOUD_INPUTS.md) 的任务工作流。实际可用性取决于已部署版本；源码、自测、部署及用户验收分别记录。

1. 在项目详情点击“编辑”，维护被测对象仓库和测试框架仓库。两个角色可以使用同一仓库。Cloud 不再有单独的项目资源页。
2. 创建 Cloud 测试任务，填写任务名称并直接粘贴完整 MR/PR 地址。可在“测试说明”补充测试环境、重点、流程、范围或需求，也可留空，由 Agent 使用已配置的工具（如 glab）查询 MR 改动及项目上下文。无需重复填写 PRD、版本、目标、流程和范围表单，不要粘贴凭据。MR 所在仓库须属于 Project 的 SUT 仓库或其下级范围；Project 使用 GitLab group 地址时，以 MR 定位该组下的实际仓库。MR/PR 地址不代表该改动已部署。
   测试说明下方提供默认折叠的“E2E 测试说明模板”。展开后可复制，MR/PR 地址自动沿用上方输入；粘贴到测试说明并替换测试环境、测试草稿占位内容。模板将 MR 变更点映射到最小必要场景、断言和证据，明确每条链路的终态；从既有资料发现环境配置，两次 subagent 基于原始材料只读审查。未知写入按原标识核对，未完成用例分别说明原因、影响和继续条件。具体业务范围由用户草稿提供，模板不内置特定业务场景。复制和展开只辅助填写，不自动创建任务或启动审查。
3. 保存草稿后，在任务详情点击一次“开始测试”。后台自动准备仓库版本，成功后下发任务，关闭页面也会继续。被测源码默认取该 MR/PR 的 head，测试框架默认取项目框架仓库的 main 最新提交，无需填写分支、SHA、检出方式或框架入口，也无需单独点击准备源码。这里的“最新”是准备时固定的提交，已下发任务不会随分支更新而变化；实际 SHA 可在源码详情中展开查看。保存草稿不会启动测试；开始请求已接受、正在准备、已排队和 Agent 已运行分别显示。
4. 在任务详情跟踪接取、执行进度和待回答问题，查看归档的分析、用例、代码、原始报告及结果。任务完成和测试通过分别显示。部署已配置原生 Harness 地址时，“测试执行”区域提供“打开 DeepSeek Harness”，在新标签页打开原生 Web UI；旁边可复制当前 Attempt 对应的会话 ID 进行定位。入口沿用 Harness 自身的登录和会话能力，不代理登录、不自动激活或续接任务，也不把打开页面计为执行或测试通过。
5. 需要复测时，在原任务明确本次范围与授权，创建独立 Attempt；原报告和结果仍可追溯。原操作结果未知时先按原身份核对，不能靠复测重发未知动作。

准备失败时不会启动 Agent；请查看失败原因后处理。若状态为“需要恢复”或原请求结果未知，应先核对原操作，不能重复点击或换一个请求绕过。确定失败后的再次开始需要新的显式操作。

项目仓库修改不回写已冻结任务。编辑草稿会采用 Project 当前仓库地址，下一次开始时重新准备版本。MR/PR 地址与实际检出版本分别记录；被测环境的部署由该项目自己的 CI 和工具负责，HyperTest 不设置预期部署版本或管理测试环境。任务输入意图不再显示旧“框架入口”；Agent 使用项目已有框架，并在执行记录中保存实际入口和命令。

旧资源页链接现在显示任务列表；旧任务快照中可能仍含历史环境信息，仅解释当时输入。当前任务的实际环境、版本和结果以 Agent/框架报告的来源及观察范围为准。
