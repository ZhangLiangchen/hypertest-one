# Cloud 原任务复测：独立执行快照与受控动作方案

状态：设计方案，未实现、未部署、未验收。普通失败任务的范围与授权确认已单独实现；本方案不表示旧受控任务已经能够重试。日期：2026-11-02。

## 问题与目标

失败是测试过程的一部分。操作者应能在原 CloudTask 中明确复测范围和本次授权，然后下发新的 CloudAttempt；前次 Attempt、测试结果、冻结输入与原操作身份保持可追溯。本方案解决旧预算任务和受控写操作不能由现行轻量 Worker 安全重试的问题，不把受控任务永久要求迁到新 Task。

指定的历史任务冻结了 `max_attempts=1`、旧范围和禁止再次运行的执行指令，并存在原动作结果不确定的历史。简单移除下发与 Worker 的旧预算拒绝会让任务排队后失败；直接复用历史 prompt 还可能重新发送未知动作。宿主薄 Worker 与 Agent 同用户，继承本机网络和可访问资源，目前没有等价的原受控 broker/隔离，不可仅靠 prompt 或确认框保证原动作不被重发。

## 每次尝试的执行快照

1. 追加独立、不可变、带版本的 AttemptExecutionSnapshot，按 Project/Task/Attempt 联合外键和唯一约束绑定；保存父 Attempt ID、原 Task 冻结 digest、明确选择的双仓 commit/环境身份、用户提供的本次测试目标/流程/范围、被授权的动作类别和目标、有效期、独立操作次数等上限、执行 profile 与策略版本、创建者及时间、规范化内容 digest。字段不得包含 token、私钥或密码；敏感凭据只保存限用途版本引用并重新授权。变更输入由新的 Attempt 快照承载，不修改原 Task manifest、历史 Attempt 和旧快照。新增快照只用于有新契约的 Attempt；历史记录保持原身份，不臆造迁移事实。
2. Web 显示原测试目标及上次执行/未知结果，明确本次范围、环境、动作与授权有效期，用户可编辑本次执行指令并逐项确认；不能让历史的“绝不再次运行”静默成为新测试命令，也不能把用户确认解释为改变未知操作结果。需要在 Task 内调整测试范围时，明确展示差异和新的完整有效范围；扩大目标、权限或凭据须由对应当前 Project/环境权限与本次明确授权共同允许，不因复测按钮自动扩权。产品需提供只读预览，服务端自行规范化并生成 digest。
3. 下发请求携带 `retry_of_attempt_id`、快照、显式范围/授权确认、`expected_version` 和新的 `operation_key`；确认绑定规范化快照 digest 与精确前次 Attempt。服务端在 Task 行锁下重查权限、有效期、旧 Attempt 已终结、当前版本及全部原操作、隔离停止和活动并发；创建快照、新 QUEUED Attempt、版本回执与审计/Outbox 同事务。相同 key 同正文返回原回执，不同正文拒绝；失答只按原 key 查询，NOT_FOUND 不自动改 key 或重发。
4. Worker 领取时按 Attempt 引用读取快照并核验 digest/版本/当前权限。源 checkout 使用该次固定双 SHA，prompt 明确以本次执行指令为当前工作范围，原 PRD 与旧禁止指令只能作为带来源的历史上下文，不能悄悄覆盖当前授权；未通过权限、profile 或隔离准入时不启动 SDK。完成与报告绑定当前快照，不能把旧结果当成本次观察。
5. 旧冻结预算及 HELD 按原合同保留，不能修改或假装结算；新 Attempt 采用明示的现行 Harness 预算语义，不继承旧的已耗尽 `max_attempts`，也不通过删除旧 hold 制造剩余额度。若需要本次外部动作次数/金额/期限上限，它们是新的受控动作授权，不等于模型预算。超出系统、环境或当前身份许可时拒绝下发。

## 受控动作的执行隔离与原 key

- 默认轻量宿主路径保留给普通任务。带受控写能力的 Attempt 需要独立受限执行 profile：由可信 Worker 在宿主通过固定、可核验配置启动隔离运行环境；Agent/项目框架不持 Docker socket、平台凭据、宿主 HOME 或真实业务密钥，不能直接访问业务网络。可采用经实际 OrbStack 验证的每 Attempt 容器（`network=none`、私有进程范围、非 root、只读系统与受限挂载），经模型专用代理和固定受控动作 broker 使用必要能力；这是受控任务的选择性隔离，不把所有普通任务恢复为容器。SDK、子代理和原生工具能否在该环境运行，必须先实测；失败保持不可执行，不降级到普通宿主进程。
- broker 在 Agent 进程外持有用途限定凭据，严格核验当前 Attempt 快照、授权、固定目标、动作参数、有效 lease/generation 和期限。沿用持久 `IDENTIFIED` → `SENT` 先记账后发送、固定请求摘要及业务终态观察；不能向 Agent 提供任意 URL、秘密或通用签名能力。模型代理与动作代理分别限域、关闭和 drain。
- 现有 `CloudActionIdentity` 的 `(task_id, action_key)` 唯一，原 identity、operation key、client/unique reference 和发送记录不可改写或转移。新 Attempt 不得对已登记的原 action key 重新授予准备/发送权。若业务上要执行一次新的独立动作，必须在新快照明确展示并授权独立动作标识和次数/金额等约束；服务端须检查其与未决原操作的语义关联，不能仅换 action key 或业务 ID 将未知的同一动作伪装成新动作。
- 只要原操作为 SENT/UNKNOWN 且缺少可信业务终态，按原 operation key 和原 provider identity 对账；NOT_FOUND、本地进程停止、HTTP 响应或操作者声明均不自动证明未执行。依现行合同未决操作阻止新 Attempt；原容器/远端的停止不能确认时保持 RECOVERY_REQUIRED。若未来允许在未决操作并存时运行只读诊断，须另行定义可验证的隔离、动作排除与状态合同，不在本方案假定。
- Worker 失联先 fence 后关闭动作代理并验证受限运行环境的原身份和停止；无法确认停止、broker drain 或外部终态时保持 UNKNOWN，不自动重新创建容器、启动 SDK 或发送动作。已发动作保留原 receipt 与业务观察；与新 Attempt 的关系只能追加，不能覆盖。

## 实施顺序和验证

1. 定义快照 schema、执行策略、数据约束与不可变迁移；统一 API、审计、读模型和任务页的范围/授权预览及确认；更新领域 §51、TMP §46、架构 §45 和 ADR-031/032 中相应现行规则。历史预算及原账本无破坏性写入。
2. 使用专用测试库覆盖旧预算任务的新快照、版本冲突、跨项目权限、确认缺失、重复/失答原 key、旧终态不可更改、旧 HELD 保留、原 UNKNOWN 与未停止运行环境拒绝等；验证并发只创建一个 Attempt。历史受控 action key 不可转移或重发。
3. 单独实现受限 profile 和 broker 接线，先用合成目标检查网络、凭据和进程隔离、固定目标及参数拒绝、SDK 工具可用性、失联 fence/停止、broker drain、原 ID 对账及不可自动重发；不能因 HTTP 健康或模拟通过而宣称真实 SUT 执行。
4. 以用户明确授权的实际任务执行功能验收，分别记录构建、部署、原操作对账和新 Attempt 的实际结果；真实外部动作由用户决定，不以该设计或自动回归代替授权。
