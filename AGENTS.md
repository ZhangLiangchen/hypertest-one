> **One Input. One Mission. One Complete Test Cycle.**

This repository is governed by four foundational documents. Any implementation, refactor, protocol change, schema change, or architecture decision MUST remain consistent with them unless an explicit Architecture Decision supersedes the relevant rule.

## Non-negotiable architecture principles

- **Two product modes, one shared Project:** Cloud creates/configures projects, creates tasks and runs their complete six-step flow in the cloud through [ADR-019](docs/architecture/ADR-019_CLOUD_TEST_TASKS_WITH_DEEPSEEK_SDK.md) and the official DeepSeek Harness Python SDK. Local preserves MCP sync under [ADR-018](docs/architecture/ADR-018_CODEX_SESSION_TASK_SYNC.md); [ADR-020](docs/architecture/ADR-020_HOOK_DRIVEN_LOCAL_SESSION_SYNC.md) designs Hooks for automatic triggers and MCP for explicit submissions / queries through one local sync coordinator, distributed as one Local release with one installer targeting Claude Code / Codex / DeepSeek harness. CloudTask and SessionTask may coexist under the same Project; Project is not configured as exclusively Cloud or Local. Cloud is **PARTIALLY IMPLEMENTED / DEFAULT OFF** as of 2026-10-23 (Asia/Singapore); its resident service on the dedicated test server has not yet been updated. The old v17 direct-DESIGN gap remains NON_PASS; earlier failures and HELD history are preserved. Contribution provenance remains runtime-reported, not independent writer proof. ADR-020 coordination / automatic adapters and the unified release / installer retain their separately owned Local delivery status; current Codex MCP sync remains available.
- [ADR-021](docs/architecture/ADR-021_SHARED_TASK_SYNC_CORE.md) designs **TaskSyncCore** as shared synchronization semantics / library: structured progress and artifact manifests, domain-specific complete-request construction, semantic differences, frozen keys / versions, isolated submission ledgers, receipt validation, UNKNOWN reconciliation and complete readback of the fixed accepted version. Local uses LocalSyncCoordinator + LocalSyncAdapter; Cloud uses CloudTaskReporter + CloudSyncAdapter in the current fenced Worker. Shared core and Cloud reporter / adapter source are present; their full acceptance remains incomplete and Local delivery is recorded separately. SDK / Hook activity is only a trigger or bounded observation, not business progress, task completion or PASS; transport state never rewrites a reported test result.
- [ADR-022](docs/architecture/ADR-022_PROJECT_MEMORY_WITH_POWERCONTEXT.md) proposes a separate **Memory Gateway** for optional Project experience reuse across Cloud / Local. Gateway / product integration is **Proposed / NOT IMPLEMENTED**; independently authorized PowerContext deployment and service-only acceptance are recorded in [service operations](docs/POWERCONTEXT_SERVICE.md). Canonical testing state, TaskSyncCore delivery and experience memory remain separate. PowerContext 1.4.0 static Bearer is a shared admin and Scope is not authorization: keep its key server-side, independently authorize query / candidate / publication, preserve source-owner privacy and filter Project / source refs. Existing `task:sync` / `cloud:work` does not grant memory access. Main / child Agents receive no service admin token; memory queues / recovery cannot block task sync or tests, and historical recall cannot prove current facts or grant tools. Initial integration uses explicit minimal queries / approved experience only, no native automatic plugins or history scans; capture disabled still permits upstream recall to transmit the current full prompt. External Generation / Embedding defaults off. See the [integration plan](docs/POWERCONTEXT_INTEGRATION_PLAN.md); no generic memory API, scope, task state or multi-tenant claim is introduced by this proposal.
- Shared synchronization does not merge SessionTask with CloudTask / CloudAttempt, add a generic write API / Task root, reuse tokens, or require a common process, global lock or journal. Local retains its real parent source, fixed actor owner, original `task:sync` and API without new server lease fields; Cloud retains `cloud:work`, Cloud typed operations and lease / generation checks. The SDK controls execution; only the Worker broker submits cloud reports, and root / child agents receive no platform writer token, DB access or Operator key. Cloud may reuse the library from its own pinned image without the end-user Local installer, three-host release or Hooks. Keep mode-specific ledgers / credentials isolated, preserve original frozen requests across recovery, and keep both modes independently operable within a shared Project.
- Product `product_mode=CLOUD|LOCAL` is an immutable task-type/source meaning derived from `task_kind=CLOUD_TASK|SESSION_TASK`, not a mutable Project switch or a conversion command. ProjectTaskSummary is a read-only query projection keyed by `(task_kind, task_id)` with mode/source labels and filtering, not a shared task FK or a new canonical task identity. Keep each type's ownership, states, history, permissions and results independent. Product modes do not reinterpret ADR-015/016 legacy `execution_mode=LOCAL|CLOUD`, HarnessMode, Connector or Runner histories.
- Session sync shares Project, stores versioned plans/cases/raw reports and reported results with source metadata, and uses scoped authorization, idempotency receipts and expected-version checks. It does not require Job, Harness, Runner, execution binding, source transfer, independent CI proof or Gate. Reported PASS/FAIL is preserved and does not become legacy VERIFIED Evidence or RELEASE_READY automatically. Sync UNKNOWN is reconciled by original key and never rewrites a test result.
- Future Hook and MCP writes share one effective local coordinator for each real parent session and retain its original Project / actor owner. A local lock or generation does not add server fencing fields or prove global exclusivity; the server retains owner / expected-version checks. Read the complete fixed-version baseline, merge only unfrozen new intentions, freeze the complete non-secret request / key / expected version, use the same existing journal, and fully read back the accepted version before declaring synced. Existing explicit MCP full snapshots, intentional empty values and frozen requests keep their original semantics; `hypertest_sync_task` is not PATCH. Do not let an event-only payload erase a plan or replace FAIL with a default NOT_RUN. Pending writes block later writes; SENT / UNKNOWN / lost responses are GET-only by original key, including after NOT_FOUND.
- Hooks are best-effort sync triggers, not business outcomes or execution authority. Stop, SessionEnd, PostToolUse, an Agent answer or a successful upload must not imply COMPLETED / PASS; subagents only contribute to the parent Task. Persist only allowed event metadata / refs / digests in the local queue and keep the transport journal compact; separately allowed private source snapshots may hold approved testing artifacts, never full chat, reasoning, raw tool payloads or secrets. Verify actual Harness version, parent-session mapping and handler / MCP readiness before using an adapter; hook metadata alone is neither trusted host proof nor Project authorization.
- The planned **HyperTest Local** release uses a future independent `local-vMAJOR.MINOR.PATCH` line, bundling MCP, private client / shared journal, coordinator, three host adapters, Hooks / allowed templates and installer / doctor / upgrade / uninstall under one fixed version / source commit. Its manifest pins bootstrap / payload digests and source validation, core / templates / adapters / installer and dependency origins / versions, MCP wire / journal compatibility, and an OS / Harness capability / acceptance matrix; components must not float independently to latest. It excludes model CLIs, model logins, Cloud SDK / runtime and platform services. Checksums verify integrity, while trusted pinned digests / signing keys and the distribution channel establish bootstrap / payload origin trust. Do not relabel historical `mcp-v0.1.0`. Installer selectors `claude-code|codex|deepseek-harness` are local host targets, not new wire provider values. DeepSeek targets an independent Local parent session, separate from the Cloud commander and its subagents; do not claim native Hooks without a versioned real probe. A validated legal plugin event bridge must still use the shared coordinator, never transcript scanning or a second writer; report unavailable triggers explicitly and retain MCP.
- Installation is a future self-service client operation, not permission to issue grants, obtain Operator keys, expand `task:sync`, register execution devices / source access through legacy Operator-key `setup` / pairing, run SUT / models, create CloudTasks or upload chats. Reuse authorized Project / client / actor and local session-selection context (not a wire field or authorization scope), or enter private authentication setup; do not put secrets in arguments, chat or receipts, switch identities after UNKNOWN, or promise one actor works for all providers. Select hosts explicitly when multiple exist; validate before backup / atomic merge, preserve other MCP / Hooks settings, retain client bindings and pending journals across reinstall / upgrade / rollback, and uninstall only package-owned configuration / binaries while preserving user sessions, projects, original journals and private exports. Installer state is local, not a server Task enum; verify native identity after actual host reload and report download, configuration, doctor, MCP, triggers and real ACK / full readback separately. Never simulate a session to begin sync or silently change global default Skills. Detailed contract: [Local release and installation](docs/LOCAL_MODE_RELEASE_AND_INSTALLATION.md).
- ADR-020 is design only and does not install or authorize background hooks, listeners or upload processes, alter user-global Skills, run tests, or expand the current default XBlock workflow. Until separately implemented, installed and accepted, use the existing native management tools under their current authorization. Hook failure / disablement must preserve explicit MCP sync; Cloud failure / disablement must not block Local sync or history.
- Local sync does not remotely start or take over the local Agent, require cloud repository/environment/model credentials, or authorize its local tools, SSH or CI. Local identifies session origin and collaboration mode, not the physical location of every test or SUT; separately authorized remote tools remain possible. Enabling, disabling or failing cloud execution must not block Local sync or historical reads, including within a mixed Project.
- CloudTask / CloudAttempt have stable platform identities separate from SessionTask and legacy TestRun. The six cloud steps are Project resources → task inputs → dispatch and freeze → DeepSeek execution/delegation → test artifacts → project-framework execution and reporting; the last two may iterate. Task inputs freeze both repository SHAs, PRD version, environment and authorization scope. HyperTest owns scheduling, resource authorization, attempt lifecycle and persisted artifacts; DeepSeek owns its internal Agent Loop and delegation to Codex / Claude Code.
- The cloud Worker calls the official Python SDK; API processes never run Agent or test commands. Each CloudAttempt gets an isolated runtime, workspace and explicit `dsh_home`. SDK idle / a child answer / successful artifact upload is not task completion or test PASS. Only the current fenced coordinator writes platform state; child agents do not create separate SessionTasks or obtain platform credentials.
- Project Git tokens and environment private keys may be encrypted and persisted by the new cloud credential design. Store task references, inject narrowly scoped runtime access, and keep secret values out of prompts, repository URLs, artifacts and logs. Model-service identities must be provisioned separately in the cloud; the SDK does not unify authentication or authorize copying local logins. Cloud shell / filesystem / framework access is confined to that profile and does not relax existing managed `native_shell=false` / `native_filesystem=false` or Connector permissions.
- ADR-017 native intake and ADR-010/012/013/015/016 execution paths remain separate compatibility/history; do not apply their execution admission rules to current management sync or alter historical results.

- HyperTest is an **Autonomous Testing Control Plane**, not another generic coding agent.
- HyperTest orchestrates **testing missions**, not model reasoning.
- General-purpose agent harnesses such as Codex and Claude Code are replaceable Testing Workers.
- **Agent performs testing work. Project test tools produce execution results. HyperTest governs evidence and conclusions.**
- Agent output is a Proposal by default; agents do not directly own Canonical Testing State.
- Agent calls each SUT's existing framework / CI; HyperTest does not build another test engine or Runner backend matrix. Formal facts require independently verified execution provenance; Agent summaries, hashes and shell self-reports are insufficient.
- [ADR-017](docs/architecture/ADR-017_NATIVE_FRAMEWORK_EVIDENCE_AND_HANDOFF.md) defines the additive `native-framework-intake/v1alpha1` profile. Native plans / cases pass Proposal / Verifier acceptance; local execution materials remain UNVERIFIED and the first native Gate only emits UNKNOWN / BLOCKED. Native Contributor handoff is explicit, sequential and fenced by a private generation-scoped capability; session labels are metadata, not native-chat identity proof.
- ADR-010 / 012 / 013 / 015 / 016 Runner-only facts, Python/pytest targets, source transfer and persistent primary-session rules continue to govern their legacy profiles and history. They do not restrict the new native profile to platform execution; native records cannot be relabeled as legacy VERIFIED Evidence or RELEASE_READY.
- Canonical chain: `Requirement → Risk → TestCase → Implementation → Execution → Evidence → Finding → Verdict`.
- Agent conversation, chain-of-thought, provider-specific event formats and temporary workspace data are not Canonical Testing State.
- BUGate remains a stateless Testing Protocol / Policy layer; HyperTest is the stateful runtime.
- Prefer PostgreSQL canonical relational state + audit log + transactional outbox for v1. Do not introduce Graph DB, Kafka, full event sourcing or a custom generic Agent Loop without a demonstrated requirement.

## Change discipline

Before changing a core domain entity, mission lifecycle, runner/evidence trust model, or agent contract:

1. Identify which foundational document owns the rule.
2. Preserve existing invariants and history semantics.
3. If the rule must change, update the corresponding specification in the same change.
4. Do not silently encode architecture decisions only in implementation code.

The goal is for HyperTest One to remain agent-independent, model-independent, evidence-driven, auditable, reproducible, and replaceable at the harness layer.
